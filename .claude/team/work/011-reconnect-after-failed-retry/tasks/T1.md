# T1 Frontend: UI state follows SessionStatus (fixes #1 (a) and (b))

Parallel with T2 (disjoint files). Plan: `../plan.md`.

## Goal
After a failed UI connect, a later connect that the UI did not start (auto-connect on plug-in)
clears the Failed marker and the stale connect error. A Failed source never shows while the backend
is connecting/connected/acquiring.

## Files
- `src/state/session.ts` (`receiveStatus`)
- `src/state/sources.ts` (doc comment of `failed` only)
- `src/components/source/status.tsx` (`activeStatus`; add a small exported helper so `SourceMenu` reuses
  the rule), `src/components/source/SourceMenu.tsx` (`entryStatus`, `detectedStatus`)
- tests: `src/state/session.test.ts`, `src/components/source/SourceButton.test.tsx` (or the existing
  test file for it), `src/components/source/status.test.ts(x)` / `SourceMenu.test.tsx`,
  `src/components/NoticeBanner.test.tsx`

## Change
1. `receiveStatus`, after the revision check and `set({ status })`: when `status.state` is
   `connecting`, `connected` or `acquiring`: `useSources.getState().setFailed(null)`; and when
   `commandErrorFrom === 'connecting'` also `set({ commandError: null, commandErrorFrom: null })`.
   Do not touch other command errors. Do not clear on `disconnected`/`disconnecting`.
2. `activeStatus` (and the menu rows): `failed` is honoured only while `state === 'disconnected'`
   and not busy connecting (backend state wins). One shared rule, no duplicated conditions.
3. Update the `failed` comment in `sources.ts`.
No IPC, Rust, bindings or `src/ui` change. No new component.

## Acceptance
- Reproduction sequence (below) ends with `failed === null`, `commandError === null`, source
  button status `connected`, banner shows nothing for the old error.
- A failed `connectTo` still ends with the row Failed and the existing banner behaviour (existing
  tests unchanged and green); a late older-revision status changes nothing.
- A non-connect command error survives status updates.

## Tests (required)

  4) out-of-order revision does not clear.
