# T7 Fix BUG-1: a Cancel/Pause click during the in-flight Start is dropped
Depends on: nothing (T1-T6 done). Parallel: no (touches the capture control and the session store).
Root cause: `bug1-rootcause.md`. Frontend fix plus one deterministic Rust regression test.

## Goal
While `busy === 'starting'` the status event can already say `acquiring`, so the main button reads
"Cancel single capture" / "Pause", but `CaptureControl.onMain` returns on `busyNow`, so the click is
lost (10-25 ms window; a 111 ms SA430 sweep then completes and is shown). A click on a control that
is labelled Cancel/Pause must never be lost.

## Contract
1. A Stop the backend receives before the sweep is published discards that sweep (already true;
   pinned by the Rust test below). Never show a frame from a cancelled capture.
2. A sweep published before the backend got Stop is a completed capture; the UI ends as
   completed, not "cancelled" (no "Single capture cancelled" announcement when a frame was shown).
3. Main-button press while `status.state === 'acquiring'` and `busy === 'starting'` queues one Stop
   that is sent right after the `start_acquisition` invoke resolves, in order (never concurrently
   with it). While `busy` is anything else ('stopping', 'applying', ...) presses stay ignored, as
   today. A second press while the queued Stop is pending is ignored (no double Stop).
4. If the queued Stop fails, the existing failure path applies (`commandError`, capture continues
   as completed, `cancelled` reset to false).

## Files
- `src/state/session.ts`: let `stop()` wait for an in-flight `start` (e.g. keep the start promise in
  the store closure and `await` it inside the stop command) while keeping `busy` coherent: it must
  not drop to `null` between the end of start and the Stop (the button must not flash enabled), and
  `busy` is `'stopping'` once the Stop is queued. Any equivalent design is fine (a `pendingStop`
  flag consumed by `start`, a command queue); keep it small and in the store, not in the component.
- `src/components/capture/CaptureControl.tsx`: `onMain` allows the press when
  `busy === 'starting' && acquiring` (call `stop()`), keeps ignoring other busy states; make
  `cancelled` only stick when the Stop actually ended the capture (derive from the result: if the
  frame count/`lastNotice` shows a completed capture, announce completion). Check the aria
  (`aria-disabled`) stays true while busy so AT users are not told it is idle.
- `src/components/capture/CaptureControl.test.tsx`, `src/state/session.test.ts`: tests below.
- `crates/spectrum-core/tests/session.rs`: deterministic regression test (below).
- Do not touch `worker.rs`/driver code. No bindings change. No new dependencies.

## Required tests (must fail on the current code)
Vitest (`CaptureControl.test.tsx` and/or `session.test.ts`, with `apiMock` from `src/test/mockApi.ts`):
- `startAcquisition` returns a deferred promise; push status `acquiring` + `captureMode: 'single'`,
  `busy: 'starting'` (or drive it via `start()`); click the main button; assert
  `stopAcquisition` has NOT been called yet; resolve start; assert `stopAcquisition` called exactly
  once, after start resolved, and `busy` was never `null` in between (subscribe to the store).
- Two presses in the same window produce one `stopAcquisition`.
- Press while `busy: 'stopping'` and while `busy: 'applying'` (acquiring) is still ignored.
- Start resolved, status `connected` already (sweep finished before the queued Stop ran): the Stop
  is still sent once (harmless: backend Stop on a stopped session is Ok) and no cancelled
  announcement is made if a frame was published (announcement text is the completed one).
- Queued Stop rejects: `commandError` set, `cancelled` reset.
Rust (`crates/spectrum-core/tests/session.rs`, next to `stop_during_a_single_sweep_discards_it`):
- Make it deterministic without sleeps: a scripted single-sweep source whose `read` signals
  "reading" on one channel and blocks until the test releases a second channel (then returns a
  full trace). Test: start; wait for "reading"; call `stop()` from a second thread (it blocks
  until the worker answers); wait until the Stop command is queued (e.g. poll a short bounded
  time, or release only after a 50 ms bounded wait on a flag set by the thread before calling
  `stop()`); release the read; join; assert state Connected, no notice, `wait_frame(0, 100ms)` is
  `None`, read count 1. A second case: stop requested AFTER the read was released and the frame
  published returns Ok and the frame stays (late cancel: contract point 2).
e2e: extend `e2e/specs/sa430.e2e.ts`'s hardware-gated block (SPECTRUM_E2E_SA430=1) with the QA
scenario: in-page click as soon as the label reads "Cancel single capture" (MutationObserver, no
delay), assert frame count unchanged and state Connected. The simulator-based acquisition e2e does
not need it (the simulator frame is instant).
